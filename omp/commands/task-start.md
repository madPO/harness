Command arguments: `$ARGUMENTS` (may be empty).

You are running **/task-start** for my engineering reflection workflow.

1. Read `skill://engineering-reflection` and `skill://engineering-reflection/templates/Task.md`. Follow the skill's private vault access and approval rules, independent of the working directory.
2. Use the task ID or description as context. Search existing task notes, including IDs and aliases. If a match exists, offer to open or review it instead of duplicating it. Never invent an ID.
3. Before implementation, ask naturally for a brief explanation. Gather the goal and reason, success and quality checks, approximate effort and confidence, risks, assumptions, unknowns, and optionally the intended first approach.
4. Reuse what I already supplied. Ask at most 1–3 targeted additional questions and allow skips. If work has started, mark expectations as retrospectively recorded.
5. Draft a concise template-based note. Prefer an existing ticket ID for a stable readable filename; otherwise use date and short slug. Set `status: in-progress` only if work actually started. Preserve consequential assumptions and uncertainty.
6. Show the exact vault-relative path and expectation snapshot. Request approval or corrections before creating the note and any necessary directories. Do not fabricate dates or results.
7. After successful creation, return its wikilink, a one-sentence expectation recap, and meaningful uncertainty. Do not create a daily journal unless explicitly asked.

Never rewrite original expectations as new information arrives. Put later developments in Progress and Outcome.
